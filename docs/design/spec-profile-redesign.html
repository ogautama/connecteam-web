Profile, redesigned

The data is right — the page just presents it as a receipt. Seventeen rows of equal weight, four identical “Lihat file” links, and the one action on the page rendered as the smallest thing on it. Same fields, same components, regrouped so the page reads like a profile — and edited one section at a time.

What’s not working

Six issues, all in IntakeSummary and the page shell around it. None require new data.

A header card holding one word The gradient bar and 110px of card exist to say “Profile” — which the account menu already said.
Seventeen rows, no hierarchy KTP number, city of school, and a spouse ID photo all get identical weight. Nothing is findable by shape.
Label left, value right Across 590px the eye has to travel a blank gap per row, and unrelated values form a false right-hand column.
Four links that all say the same thing “Lihat file” ×4 gives no sense of what was uploaded or whether it’s the right file — you open a tab to find out.
An em-dash where state should be “Foto KTP Pasangan — ” reads as missing data. It’s optional, and only the form knows that.
One button, seventeen fields Fixing a typo in a phone number reopens all sixteen inputs and five upload pickers.

Is per-section editing actually cheap?

Yes — and it needs no change to submitJoinData or the database.

Why it works as-is

  • The client already holds the whole saved record. A section save sends the full MemberIntakeInput with only that group’s fields swapped in — every other value goes back unchanged.
  • All the action’s validation still passes, because the untouched fields were already valid when they were saved.
  • uploadIfNeeded already skips fields with no new file and passes the existing storage key through, so editing Identitas never re-uploads a photo.
  • One state change: editing: boolean becomes editingSection: "kontak" | "identitas" | "pendidikan" | null.

What to watch

  • Last write wins. Because each save rewrites the whole row, a second tab open since before your edit would push its stale values back. Cheap fix: re-read the record on save and merge, or narrow the action to accept a partial.
  • More saves, more side effects. Each call also runs createPendingInvite and revalidatePath. The invite is a no-op today — the email always resolves to an existing user — but three saves now fire it three times.
  • First fill is unchanged. A member with no record still gets the full one-question-per-card form; sections only appear once there’s something to edit.

Decided

  • Pengundang / Unit is not editable — by anyone, from this page. It renders as a chip in the header with no edit path; it belongs to no section’s “Ubah”, and section saves always send the stored value back unchanged. It resolves the member’s leader and feeds PendingInvite, so changing it means re-parenting the member in the tree — not a profile edit.
  • No KTP is masked by default. Last four digits visible, full value behind a “Lihat” toggle. Client-side reveal of a value the client already has — no server change. The Identitas editor shows the full value, since editing requires it.
